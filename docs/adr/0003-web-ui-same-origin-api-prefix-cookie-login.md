# The Core serves the web UI on the same origin, the API lives under /api, and browsers log in with a cookie

The Core serves the web UI's static files from `wwwroot` without auth, and the whole API moves under `/api/`, so UI routes can never collide with API paths (`/inbox` and `/done` were both). A browser logs in once by posting the secret to `POST /api/session`; the Core answers with an `HttpOnly; SameSite=Strict; Path=/api` cookie whose value is an HMAC derived from the secret, and from then on accepts either that cookie or the `Bearer` header the CLI and tray app keep using. Deriving the cookie from the secret means no session store and no Data Protection keys on disk, and changing the secret logs every browser out (logout only clears the browser's copy; a copied cookie stays valid until the secret changes). Cookie-authenticated writes are also checked against the `Origin` header, which covers bodyless POSTs such as done, archive, restore and the later backup upload that `SameSite=Strict` alone does not, because every port on `127.0.0.1` is the same site. Scripts in the page can never read the secret, which matters once the Core runs on a remote server. We rejected keeping the secret in `localStorage` and sending it as `Bearer` (simplest, but any XSS leaks the secret), a one-time token handed over by the tray app (ties the web UI to the desktop), hash routing to avoid the path collision (no Core change, but ugly URLs and it did not fit SvelteKit, ADR 0004), and serving the UI under `/app/` (moving the API was cheap while only our own Clients use it).
